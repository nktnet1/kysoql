## Basic conditions

Repeated `where` calls are combined with `AND`. Values are passed separately
from field names, never interpolated into a SOQL string:

```ts
import { db } from "./db";

const query = db
  .selectFrom("Account")
  .select(["Id", "Name"])
  .where("Name", "like", "Acme%")
  .where("AnnualRevenue", ">=", 100_000);
```

## Operators and values

| Operator | Accepted values and restrictions |
| --- | --- |
| `=`, `!=` | Field-appropriate values; `null` only when the generated field permits it. |
| `<`, `<=`, `>`, `>=` | Ordered field types and non-null values. |
| `like` | Supported string-like fields and a string pattern. |
| `in`, `not in` | Non-empty homogeneous, field-appropriate lists; compatible ID/reference subqueries are also supported. |
| `includes`, `excludes` | Non-empty lists of generated active values for multipicklist fields. |

Operator names are lowercase in TypeScript; emitted SOQL uses uppercase
keywords. `is`, `is not`, `between`, `ilike`, `not like`, and SQL `exists` are
not part of this API. To negate a supported predicate, use `eb.not(...)`.
Location fields require [distance expressions](/docs/framework/guides/geolocation).

Null uses `where("Field", "=", null)` or `"!="`, not a string containing
`"null"`. Date/time fields use [literal helpers](/docs/framework/guides/literals), not plain
strings or JavaScript `Date` objects.

## Group AND, OR, and NOT

The expression builder is callable as `eb(field, operator, value)` and exposes
`and`, `or`, and `not`:

```ts
import { db } from "./db";

const query = db
  .selectFrom("Account")
  .select(["Id", "Name"])
  .where((eb) =>
    eb.and([
      eb.or([
        eb("Name", "like", "Acme%"),
        eb("Name", "like", "Example%"),
      ]),
      eb.not(eb("Name", "like", "%Test%")),
    ]),
  );
```

Use non-empty groups; do not depend on empty `and([])` or `or([])` having an
SQL-style identity. Build optional conditions with
[`$if`](/docs/framework/guides/composition) instead.

## IN and NOT IN lists

```ts
import { db } from "./db";

const ids: readonly string[] = ["001000000000001AAA"];
if (ids.length === 0) {
  throw new Error("Choose at least one account ID");
}

const query = db
  .selectFrom("Account")
  .select(["Id", "Name"])
  .where("Id", "in", ids);
```

An empty list is rejected. For application helpers, decide explicitly whether
an empty input means "no matches", "invalid request", or "omit this optional
filter". Omitting an authorisation filter can unintentionally widen a query.

For related-record existence checks, use a
[semi-join or anti-join](/docs/framework/guides/relationships#semi-joins-and-anti-joins)
instead of first fetching all IDs into JavaScript.

## Multipicklists

This example requires a custom multipicklist `Account.Interests__c` whose
Describe metadata includes active values `Email` and `Events`:

```ts
import { soqlMultiSelectAnd } from "@kysoql/core";
import { db } from "./db";

const eitherValue = db
  .selectFrom("Account")
  .select(["Id", "Interests__c"])
  .where("Interests__c", "includes", ["Email", "Events"]);

const bothValues = db
  .selectFrom("Account")
  .select(["Id", "Interests__c"])
  .where(
    "Interests__c",
    "includes",
    soqlMultiSelectAnd("Email", "Events"),
  );
```

A value array compiles to Salesforce's comma-separated OR form.
`soqlMultiSelectAnd(...)` compiles the same generated active values into the
semicolon-separated AND form. It can also appear inside the value array to express
Salesforce's mixed form, for example `[soqlMultiSelectAnd("Email", "Events"),
"Other"]` for `(Email AND Events) OR Other`. These helpers stay typed against the
generated picklist. `soql.raw()` remains the explicit unsafe escape hatch for trusted
SOQL that the builder does not model. Apex has a separate
[bind-left INCLUDES form](/docs/core/apex/bindings#bind-left-includes).

## LIKE patterns and input safety

Plain strings keep Salesforce LIKE semantics, so `%` matches zero or more
characters and `_` matches one character:

```ts
import { db } from "./db";

const patternQuery = db
  .selectFrom("Account")
  .select(["Id", "Name"])
  .where("Name", "like", "Acme_%");
```

When user input should be matched literally, wrap it with `soql.likeLiteral()`.
The helper escapes `%` and `_` as LIKE metacharacters while the compiler still
escapes quotes and backslashes as SOQL string content:

```ts
import { soql } from "@kysoql/core";
import { db } from "./db";

const search = "50%_off";
const literalQuery = db
  .selectFrom("Account")
  .select(["Id", "Name"])
  .where("Name", "like", soql.likeLiteral(search));
```

Object names, field/relationship references, aliases, operators, and other
identifier-bearing query parts are runtime-validated as well as typed. Keep an
application allowlist for which valid fields a caller may choose: syntax
validation blocks arbitrary SOQL syntax in those inputs, but it is not
authorisation. See
[security](/docs/core/reference/security).

## Raw SOQL escape hatch

For syntax Kysoql does not model yet, `soql.raw()` emits a trusted fragment
verbatim:

```ts
import { soql } from "@kysoql/core";
import { db } from "./db";

const query = db
  .selectFrom("Account")
  .select(["Id", "Name"])
  .where(soql.raw("CALENDAR_YEAR(CreatedDate) = 2026"));
```

`soql.raw()` deliberately bypasses identifier validation and value escaping.
Only use it with trusted, application-owned SOQL. Never concatenate or
interpolate request data, form values, search terms, IDs, or other untrusted
input into a raw fragment. Prefer normal builder values or `soql.likeLiteral()`
for user-controlled data.

## Filters over functions

Expression callbacks also expose date functions, `toLabel`, and `distance` via
`eb.fn`. Supported beta arithmetic lives under `eb.beta`, not `eb.fn`.
See [date functions](/docs/framework/guides/date-functions),
[translated labels](/docs/framework/guides/select-functions#translated-labels), and
[experimental features](/docs/core/advanced/experimental).
