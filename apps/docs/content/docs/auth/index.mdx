`@kysoql/auth` obtains Salesforce bearer tokens for applications that execute
SOQL through [`@kysoql/rest`](/docs/rest). Authentication is separate from query
construction and transport, so applications can choose the Salesforce flow that
matches their deployment model.

For most applications, use the `SalesforceAuth` class. It binds the Salesforce
login/site URL and client ID once, then exposes the supported flows as methods.
The lower-level functions remain available for custom composition.

For a server-to-server integration that can protect a private key, the default
Kysoql path is Salesforce's **OAuth 2.0 JWT bearer flow**. It avoids interactive
login and does not require storing a client secret or refresh token.

<SalesforceReference title="OAuth 2.0 JWT Bearer Flow for Server-to-Server Integration" href="https://help.salesforce.com/s/articleView?id=xcloud.remoteaccess_oauth_jwt_flow_ca.htm&language=en_US&type=5" />

## Server-to-server with a private key

```ts
import { SalesforceAuth } from "@kysoql/auth";
import { createRestExecutor } from "@kysoql/rest";

const auth = new SalesforceAuth({
  loginUrl: "https://login.salesforce.com",
  clientId: "external-client-app-id",
});

export async function createSalesforceExecutor() {
  const authenticate = () =>
    auth.jwtBearer({
      username: "integration@example.com",
      privateKey: { type: "file", path: "./salesforce-auth-key.pem" },
    });

  let session = await authenticate();
  const instanceUrl = session.instanceUrl;

  return createRestExecutor({
    instanceUrl,
    accessToken: async ({ refresh }) => {
      if (refresh) {
        const next = await authenticate();
        if (next.instanceUrl !== instanceUrl) {
          throw new Error("Salesforce instance changed; recreate the REST client.");
        }
        session = next;
      }
      return session.accessToken;
    },
  });
}
```

Keep the signing key server-side. `privateKey` uses an explicit source object:
`{ type: "file", path }`, `{ type: "pem", value }`, or
`{ type: "crypto-key", key }`. Kysoql does not guess whether a string contains
PEM data or a file path.

See [JWT bearer](/docs/auth/flows/jwt-bearer) for Salesforce setup, assertion
details, and renewal behaviour.

## Other supported flows

Use [authentication flows](/docs/auth/flows) to choose another supported method.
The flow guides are grouped under the **Authentication flows** section in the
navigation, with JWT bearer first as the server-to-server default.

Salesforce's retiring username-password, user-agent, and hybrid user-agent flows
are intentionally not implemented. Asset tokens identify connected devices and
are not general bearer sessions for SOQL REST access.

<SalesforceReference title="OAuth Authorization Flows" href="https://help.salesforce.com/s/articleView?id=remoteaccess_oauth_flows.htm&language=en_US&type=5" />

## Token lifetime and persistence

JWT bearer never returns a refresh token. When used with `@kysoql/rest`, provide
an access-token provider so the REST client can cache the current access token in
memory and obtain a replacement JWT session after `401 INVALID_SESSION_ID`. See
[JWT bearer](/docs/auth/flows/jwt-bearer#cache-and-renew-the-access-token).

## Refresh-token persistence

Flows that issue refresh tokens can use the built-in memory, browser
`localStorage`, Redis, or custom stores. See
[refresh-token storage](/docs/auth/storage). Rotation is persisted before a newly
refreshed session is published to the caller.

## Functional API

The standalone helpers such as `authenticateJwtBearer()`,
`exchangeAuthorizationCode()`, and `refreshAccessToken()` remain exported. Use
them when you want each operation to receive its full configuration explicitly,
or when building a higher-level abstraction of your own.
